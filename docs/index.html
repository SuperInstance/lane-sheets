Lane Sheets — SuperInstance

An agent workflow written as one JSON sheet — lanes of cells connected by piping only — so the same workflow can be read as a spreadsheet, run by a reference interpreter, lifted to LangGraph or LangChain code, or hosted against a real model. The sheet is the layer one step below the frameworks, the way a hardware description sits below the languages compiled from it. Run state is derived from the sheet, never stored in it; cells touch only through named piping, never through each other's interiors — and a cell can itself contain a whole sheet, opaque from the rung above it.

Three lifts and a host



  

    
LangGraph

    

      lanesheet/lift_langgraph.py raises a sheet to a standalone
      LangGraph module. On the full conformance corpus the lifted module's
      trace is byte-identical to the interpreter's:
      27/27 (19 positive traces + 8 named refusals).
      The LangGraph module shows the sheet's shape — the piping
      topology as a graph.
    

    
LangChain (LCEL)

    

      lanesheet/lift_langchain.py targets LangChain's runnable
      core — langchain-core only, never the full package — and
      also lands 27/27 byte-identical. Branching is carried
      by RunnableBranch (its laziness betrays nothing: the arms
      are upstream cells, already computed) and each by
      RunnableEach. The LangChain module shows the sheet's
      schedule rather than its shape — same execution, different
      auditability. The per-construct mapping is in
      LANGCHAIN.md.
    

  

  

    
The host: real models, honestly labelled

    

      The Python host binds the llm/tool names in a
      sheet to real providers — MiniMax first. A live run emits the same
      canonical trace behind a header record that names the run live and the
      providers behind it; run_host_check.py validates a live
      trace structurally (hashes recompute, order, value flow) — never
      byte-equality, because live output is nondeterministic. A stub trace
      dressed as live fails the checker; a tampered hash fails by name.
      Captured live traces, including one whose llm cell sits a
      rung down inside a sub-sheet, are in the repo's
      examples/;
      the binding layer and the two-tier law are in
      HOST.md.
    

    
Refusals are named and total

    

      A sheet that cannot run exactly is refused with a specific error —
      CycleDetected, RecursiveSheetRef,
      BindTargetNotValue, EachTooManyElements, … —
      in the interpreter, both lifters, the host, and the browser port above.
      Nothing is silently approximated.
    

  





The downward record



  Downward, workflow constructs map onto the Quilt fabric's opcodes
  (BIND/LINK/EFFECT/VIEW/TICK, with ACK/NAK argued as the +1): of ten
  constructs, two map cleanly, six with named losses, two not at all yet
  (DOWNWARD.md).
  For the clean subset there is a real QUF writer and reader — container
  bytes per the QUF spec, round-trip reconstruction, agreement by the
  fabric's canonical hash, 45/45 checks including the spec's
  own published golden vector. The fabric itself has consumed one of these
  images: the quilt-verilog RTL loader booted from it in Icarus Verilog
  simulation (RUN reached, readbacks byte-exact) — simulation, not silicon
  (FALSIFIER.md).
  Two honest findings came out of that work: the QUF spec's crc32 digest
  scope is underdetermined — the Python tooling digests all sections, the
  RTL loader only its four payload sections — filed as
  QUF-NOTES D9
  with a --no-crc32 writer flag rather than a unilateral
  ruling; and driving the booted fabric through the mapped op sequence
  shows its state agrees at the bind layer (dials byte-exact, hash
  identical) and diverges at the run layer in five named places —
  an unpaired inject silently dropped, a directed edge costing two LINKs, a
  THRESH=0 sink oscillating and training its own upstream synapse, metabolic
  decay erasing an activation in one tick, and numeric regimes that never
  meet
  (BEHAVIOUR.md).
  What a real QUIL compiler must compensate for is listed there, from
  measurements.




Sheets as git.pp records



  A lane sheet also compiles to git.pp
  records — one record per cell, parents as piping ancestry — and
  reconstructs by the fold alone: arrival order shuffled, state
  identical, interpreter trace byte-identical to the golden (11/11,
  GITPP-SPIKE.md).
  Conflict behaviour is executed, not argued: an override record wins a
  cell's definition, a descendant redefinition dominates its ancestor, an
  equal-class sibling loses and is named. The live proof: the public repo
  patchwork-quilt/gitpp-dogfood-sheet
  carries a nested, reused sheet as pure records, and the released
  gitpp-action derived them in real GitHub CI
  (run 40361763003, success) —
  its state agreeing with the independent local fold on all 20 keys, zero
  divergences
  (DOGFOOD.md).
  Installing a plugin sheet is landing its records; uninstall is honestly
  not a fold operation yet.
